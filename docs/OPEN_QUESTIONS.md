# Bombyeol — 미결정·검증 필요 목록

구상 대화와 이번 기반 작업에서 **아직 답이 없거나 가정으로만 둔 것**. 해결되면 해당 문서에 반영한 뒤 여기서 지운다(또는 "해결" 표시). 사용자가 "놓친 게 있을 수 있다"고 요청했으므로 질문을 넓게 적었다.

## A. 결정이 필요한 것 (사용자)

### Q-PAY — 결제 공급자 ⚠️ 이전 결정이 뒤집힐 수 있음
- 이번 조사에서 **Stripe는 한국에서 사업하는 사업자 계정을 개설할 수 없고 한국 은행 계좌로 정산도 안 된다**는 자료를 확인했다(Stripe 자체는 한국 카드·카카오페이·네이버페이 결제 수용은 지원하나 계정은 EU/HK/UK/US 등 지원 국가 법인 필요).
- 사용자는 대화에서 "Stripe로 시작"을 선택했으나 이 전제가 흔들린다. **hamkke의 Phase 5(Stripe)에도 같은 문제가 있을 수 있다** — hamkke 출시 시 확인 필요.
- 선택지: (a) 국내 PG(포트원 + 토스페이먼츠 등, 사업자등록·정기결제 계약 필요), (b) 해외 법인/대행(MoR: Paddle 등, 개인 셀러 지원 여부·수수료 조사 필요), (c) 무료 출시 후 결제 후속.
- **선결 질문**: 개인사업자(또는 법인)를 등록할 계획인가? 그렇지 않다면 (b)/(c). Phase 8 착수 전까지 결정.
- **결정 자료(2026-10-01)**: [`research/2026-10-01-q-pay-providers.md`](research/2026-10-01-q-pay-providers.md) — 공식 문서 기준 비교표(토스페이먼츠·포트원 V2·Paddle·Polar·Lemon Squeezy 등). 요약: 사업자 등록 시 포트원 V2(+토스페이먼츠, 예약 결제로 자체 스케줄러 불필요) / 미등록 시 Paddle(대안 Polar) / (c) 무료 출시. 일부 가입 조건·수수료는 검색 요약 근거라 계약 전 재확인 표시. 구현은 사용자 선택 후.

### Q-LOGO — 로고 확정
- `image-asset/logo`의 SVG는 보드 1번 심볼을 단순화한 거친 버전. 그대로 쓸지, 보드 기준으로 다시 제작할지, 어디에 쓸지(앱 아이콘·워드마크·OG) 결정.

### Q-FONT — 손글씨 폰트
- 온글잎 제작 서비스 종료, 후보 폰트별 웹폰트·앱·PDF 임베딩 라이선스 미확인. 아이용/조부모용 두 폰트를 실제로 원하는가, 아니면 Pretendard 단일 + 일러스트로 톤을 구분할까.

### Q-HONOR — 어르신 대상 경어 수준 (2026-10-01 추가) — B안 선택으로 **잠정: 해요체 + 어르신에게 보이는 곳만 "~세요"**(사용자 확인 시 확정)
- 토스·당근 라이팅 가이드는 모두 "존칭 최소화"(~시겠어요·여쭈다 지양). 봄별의 주 사용자는 조부모. 해요체는 유지하되 조부모에게 보이는 문구(질문 카드·온보딩)에 "~세요/~셨어요"를 허용할지 결정. 목업은 안마다 다르게 적어 비교(`docs/mockups/2026-10-01-ds/`).

### Q-ILLUST — 빈 화면·질문 카드 일러스트
- 손그림 일러스트를 직접 그릴지, 생성할지, 쓰지 않을지(`DESIGN.md` §9.3). 목업에는 넣지 않았다.

### Q-STORYBG — 이야기 탭 배경 — **해결(2026-10-02): B안 선택 → navy 배경 유지**(DESIGN §6). 다크에서도 navy(§3.1)
- `DESIGN.md` §6은 이야기 탭 navy 배경. 탭 전환 눈부심(어르신) 대안으로 paper 배경 + navy 띠를 목업 안 C로 비교. 고르면 §6 갱신.

### Q-README·Q-HOOK — main에 넣어도 되는 최소 파일
- `main`은 개발 커밋만. **README.md(실행법)**, **`.claude/settings.json`(SessionStart 훅)**, `.env.example`, `wrangler.toml` 같은 개발 설정은 main에 두는 것으로 가정했다. 이 가정이 맞는지, 아니면 README도 docs 브랜치로 뺄지 확인.

### Q-DOMAIN — 도메인·상표
- `bombyeol.*` 도메인 확보 여부, "봄별" 상표·앱스토어 이름 충돌(흔한 이름) 확인. OAuth Redirect·Cloudflare 배포·처리방침 URL의 전제.

### Q-PRICE — 가격·한도 확정
- PRD §5의 수치는 초안. 실제 단가 재확인 후 가격(월/연)·한도 결정. 연간 요금제·평생 이용권·"책 한 권" 단건 결제 모델도 후보.
- 2026-10-01 사용자 승인: Phase 1~3 `plan.ts` 상한·리밋 수치(무료 relative 0, 반려동물 3/10, 글 기록 300/일, 좋아요 300/h, 댓글 60/h 등)를 **결제 전 운영값**으로 확정. 가격 결정 시 다시 본다.

### Q-SCHED — 정시 알림
- 기념일·생일 정시 푸시가 필요한가. Cloudflare Cron Triggers로 가능하지만 hamkke는 pull 방식으로 미뤘다. 가족 앱에서 생일 알림은 기대가 큼.

### Q-ELDER — 어르신 실제 사용 시나리오
- 실제 사용할 어르신(부모님?)이 있는가. 스마트폰 기종(Android/iOS), 카카오톡 사용 숙련도, 글자 크기 설정 습관을 알면 알림·로그인 경로(웹푸시 vs 카카오톡 공유) 우선순위가 정해진다. 소수라도 사용자 테스트 계획이 필요.

### Q-LAUNCH — 출시 범위
- 첫 사용자는 누구인가(본인 가족만? 공개 출시?). 공개 출시라면 약관·처리방침·전문가 검토·사업자 요건이 필수, 본인 가족용이면 범위를 좁혀 먼저 검증할 수 있다(스코프 축소 금지 원칙과 별개로 "배포 대상" 결정).

### Q-EXPORT — 내보내기·이탈
- Space 삭제 유예 기간(30일?), 구독 만료 후 읽기 전용 기간, 원본 ZIP 내보내기 범위.

## C. hamkke와의 교차 이슈 (봄별 밖)

- hamkke의 Stripe 계정 개설 가능 여부(Q-PAY와 동일 문제).
- hamkke 점검 결과 중 아직 적용되지 않은 금전 리스크(재구독 unique 충돌, R2 업로드 상한, 계정 삭제 등)는 hamkke `docs/COMMIT_PLAN.md`에 커밋 단위로 추가할지 사용자 결정이 대기 중(hamkke 세션에서 "원하시면 추가"로 끝남). 봄별 설계는 이를 이미 게이트로 반영했다.
