# Bombyeol — 개발 방법론 (고정 문서)

hamkke의 커밋 컨벤션을 계승하되, **히스토리 정책을 바꿨다**: `main`에는 개발 작업만 남기고, 문서·에셋·세션 기록은 `docs` 브랜치에서 **사용자가 지시할 때만** 커밋한다.

레퍼런스: `products/hamkke/docs/WORKFLOW.md`(직접 계승), `nodejs/*`, `products/typography-design`.

## 1. 커밋 메시지 형식 (hamkke와 동일)

```
type(scope): 한국어 메시지
```

- **type**: `feat` `fix` `refactor` `chore` `test` `refine` (`docs`는 main에서 쓰지 않는다 — §4). `refine` = 이미 동작하는 기능의 디자인·인터랙션 다듬기. 새 동작이 생기면 `feat`.
- **scope**: 도메인 슬러그. 예: `auth` `space` `media` `moment` `story` `pregnancy` `push` `billing` `privacy` `design-system` `i18n` `infra` `prisma` `a11y` `motion`.
- **메시지**: 한국어 담백한 서술체, "~구현/~수정/~추가/~재구성"으로 끝맺음. 본문(body)은 쓰지 않는다. (도구가 붙이는 `Co-Authored-By` 트레일러는 허용.)
- **비용 게이트가 걸린 커밋**은 제목에 게이트를 서술하지 않아도 되지만, 테스트에 `G-xx` 표기를 남긴다(`COST_GUARDS.md` §2).

## 2. 커밋 단위 (원자성)

- 관심사 하나당 커밋 하나. 스키마 정의(`chore(prisma)`)와 기능(`feat`)은 hamkke처럼 분리.
- 동작 먼저, 폴리시 나중(`refine`). 순서를 뒤집지 않는다.
- 커밋이 많아지는 것을 두려워하지 않는다.
- 실제 순서는 `COMMIT_PLAN.md`에 고정. 벗어나야 하면 **커밋 전에** 그 문서를 먼저 갱신한다(작업 트리에서 수정, 커밋은 §4).

## 3. 브랜치 전략

- `main`: 개발 커밋만. 항상 빌드·테스트 통과 상태.
- 기능은 작업 브랜치에서 진행한 뒤 `main`으로 **머지 커밋**(squash 금지, 원자적 히스토리 보존). 클라우드 세션은 세션이 지정한 브랜치명(예: `claude/...`)을 쓸 수 있으므로 이름은 강제하지 않되, **머지 시 히스토리를 뭉치지 않는다**.
- `docs`: 고아 브랜치. `main`과 공통 조상이 없다. 문서·에셋 전용.
- `spike/*`: 스택 검증 스파이크(`ARCHITECTURE.md` §9) 전용, **main에 머지하지 않는다**. 결과는 `PROGRESS.md`에 기록.

## 4. 문서 커밋 정책 (사용자 결정, 2026-10-01)

| 종류 | 어디에 | 언제 커밋 |
|---|---|---|
| 개발 코드·테스트·설정 | `main`(작업 브랜치 경유) | `COMMIT_PLAN.md` 단위마다(자율) |
| 문서(CLAUDE.md, docs/**), 에셋(image-asset/**), 세션 기록 | `docs` 브랜치 | **사용자가 "docs 커밋"을 지시할 때만** |

- 작업 도중 문서(`COMMIT_PLAN.md` 체크박스, `PROGRESS.md`, 설계 갱신)는 **작업 지속을 위해 자유롭게 수정**한다. 다만 수정만 하고 커밋하지 않는다.
- 세션을 옮겨야 할 때(컨텍스트 소진, 키 대기, 기능 단위 마무리 등) Claude는 **먼저** "docs 커밋이 필요합니다"라고 알린다. 사용자가 지시하면 그때 `.docs/` 워크트리에서 `docs` 브랜치에 커밋·푸시한다.
- docs 커밋 메시지 형식: `docs: 세션 인수인계 — <한 줄 요약>`(예: `docs: 세션 인수인계 — Phase 1 인증 구현 완료, 카카오 키 대기`). 한 세션에 여러 번 커밋하지 않고 지시된 만큼만.
- 커밋되지 않은 문서 수정은 클라우드 VM이 회수되면 사라진다 — 감수하는 정책이지만, 세션이 비정상 종료될 위험이 있는 큰 변경 뒤에는 사용자에게 알린다.
- `main`에는 `docs:` 타입 커밋이 **없다**. README.md·설정 주석처럼 코드와 함께 바뀌는 최소한의 개발 문서만 개발 커밋에 함께 넣을 수 있다(README 위치는 `OPEN_QUESTIONS.md` Q-README).
- 세션 대화 기록(devlog jsonl)은 리포에 넣지 않는다. 보관이 필요하면 `docs` 브랜치에만, 키·개인정보를 붙여넣지 않는 것을 전제로(사용자 결정).

## 5. 진행 순서

`COMMIT_PLAN.md` 참고. 요약: 스파이크 → 부트스트랩 → 인증·Space → **미디어 파이프라인(비용 게이트)** → 오늘 → 이야기 → 우리·임신 → 알림 → 삭제·개인정보 → 결제 → PWA·릴리스 → Android → 디자인 폴리시(상시).

hamkke와 다른 점: (1) 비용 방어가 별도 Phase가 아니라 각 기능의 완료 조건, (2) 삭제·개인정보 기능이 출시 직전이 아니라 미디어 저장을 시작하는 시점과 함께 설계, (3) 결제 공급자가 미정이라 결제 Phase 앞에 결정 게이트가 있다.

## 6. 일반 원칙

- 빨리 만든다가 아무렇게나 만든다를 뜻하지 않는다.
- 스코프를 인위적으로 줄이지 않는다(PRD V1 = 전체 기능).
- 외부 서비스 화면·네이티브 다이얼로그처럼 자동화 도구가 조작할 수 없는 검증은 `PROGRESS.md`의 "미완료 검증 항목"에 남기고 사용자가 직접 확인한다.

## 7. 환경변수 요청 규칙 (hamkke 규칙 계승 + 클라우드 보강)

- 사용자에게 키를 요청하기 전에 `.env.example`(main, Phase 0에서 생성)과 `docs/ENV_MANIFEST.md`에 이름·형식·발급처·필요 시점을 먼저 채운다. 말로만 요청하지 않는다.
- 아직 설계가 확정되지 않은 Phase의 변수는 추측해서 채우지 않는다(결제 공급자 등).
- 로컬 `.env`에 생성 가능한 값(랜덤 시크릿)은 직접 생성한다. 외부 계정 발급이 필요한 값만 사용자에게.
- **키 값은 대화에 붙여넣지 않게 안내한다.** 클라우드 절차는 `CLOUD_SESSION.md` §3.
